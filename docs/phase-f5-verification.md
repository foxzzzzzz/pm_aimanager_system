## 4. 必须由用户确认的人工验收

以下项目涉及真实微信身份、设备渲染、管理员登录态或外部消息渠道，Codex不能代替用户给出最终结论。

### M01 Web登录后视觉

1. 打开 `http://localhost:15173/`，输入本地管理员令牌并选择验收项目。
2. 检查“项目看板”“问题与审计”中的问题新增审批、问题删除审批和节点变更审批。
3. 确认列表包含提交时间，按钮加载/成功/失败状态清晰，目标浏览器无横向溢出、遮挡或错位。

回传：`M01 通过/失败 + 浏览器名称和版本 + 失败截图或现象`。

### M02 微信真机基础与“我的”

1. 使用普通编译及真机调试打开小程序。
2. 确认项目、问题、消息、我的四个入口可用；“我的”按项目分组并显示待办/近期/逾期/已完成数量。
3. 核对“我的”只显示当前成员承担R或A的任务，角色标签和进入看板、返回流程正确。

回传：`M02 通过/失败 + 手机型号/系统 + 当前绑定成员姓名 + 失败截图或现象`。

### M03 真实人员归属与项目经理权限

1. 核对团队Sheet中的项目经理姓名、手机号与后台成员绑定信息。
2. 分别使用一个普通成员账号和项目经理账号进入小程序。
3. 普通成员不应看到问题审批队列；项目经理应看到本项目全部问题审批，可处理本人提交的节点申请。

回传：`M03 通过/失败 + 项目编码 + 普通成员姓名 + 项目经理姓名 + 不一致项`。不要回传完整手机号、openid或令牌。

### M04 重点问题新增批准

1. 普通成员登记测试问题，R指定为任意正式团队成员，A必选，C/I按需选择。
2. 审批前确认正式问题列表、风险统计和提醒中均不存在该问题。
3. 项目经理在小程序批准；确认正式问题出现、RACI一致，提交人收到站内结果消息。

回传：`M04 通过/失败 + 测试问题标题 + 申请提交时间 + 审批端 + 结果消息是否收到`。

### M05 重点问题新增驳回

1. 再提交一条测试问题并由项目经理驳回。
2. 确认问题未进入正式列表和统计，提交人收到驳回消息。

回传：`M05 通过/失败 + 测试问题标题 + 是否未进入正式列表 + 消息是否收到`。

### M06 删除审批

1. 对M04已批准问题发起删除申请；审批前确认原问题仍可见并保持原状态。
2. 先用一条申请验证驳回后问题保持不变；再申请并批准删除。
3. 确认批准后问题关闭、退出活动风险列表，提交人收到结果消息。

回传：`M06 通过/失败 + 问题标题 + 驳回后状态 + 批准后状态 + 消息是否收到`。

### M07 跨端看板与业务语义

1. 在同一时间分别查看Web项目看板、小程序项目看板和“我的”。
2. 核对待办/近期/逾期/已完成数量、问题风险摘要和节点RACI符合真实业务预期。
3. 特别确认近期范围为今天至未来14天，逾期项醒目且没有跨项目数据。

回传：`M07 通过/失败 + Web四类数量 + 小程序四类数量 + 不一致的节点/问题`。

### M08 真实通知与停止提醒

1. 在已授权的微信订阅消息渠道中准备一条到期或逾期测试问题。
2. 确认R/A收到预期提醒，C/I不收到高频提醒；同一业务日重扫不重复。
3. 将问题通过删除审批关闭或置为已解决，下一次扫描确认不再提醒。
4. 短信仅在域名、签名、模板和通道均完成正式配置后验收，不作为当前本地F5阻塞项。

回传：`M08 通过/失败/微信通道未配置 + R/A是否收到 + C/I是否未收到 + 重扫是否重复 + 关闭后是否停止`。

## 5. 推荐执行顺序

1. Codex完成A01至A10；任一失败先修复并重新全量回归。
2. Codex完成J01至J03；Docker环境问题才需要用户协助回传输出。
3. 用户先完成M01至M03，确认运行环境、界面和账号权限基线。
4. 用户按M04、M05、M06顺序完成新增、驳回和删除端到端流程。
5. 用户完成M07和M08；未配置真实微信通道时，将M08明确记录为外部阻塞而非“通过”。
6. Codex汇总证据、处理缺陷并更新PRD、PLAN、CHANGELOG、TodoList和运维文档；全部阻塞项关闭后再申请Phase F5提交确认。Tag需另行确认。
